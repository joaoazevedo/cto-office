Hold a one-to-one with a member of the office. Usage: `/1on1 <member>`

This is how they improve. Treat it as a real 1:1: mostly calibration, occasionally a correction,
never a performance review.

## Run it

1. **Read** the member's current `LEARNED.md`. Locate the OS repo with `cto root` — never assume a
   path, it is cloned wherever the user put it. The file is at `<root>/experts/<slug>/LEARNED.md`
   or `<root>/coordinators/<slug>/LEARNED.md`. Queued notes are in `<root>/.notes/<member>.md`.

2. **Open with what you have.** Show the queued notes in one compact list. If there are none, say so
   and ask them directly: what has this member got wrong lately, and what has it got right that it
   should keep doing.

3. **Propose concrete edits.** Each lesson is one line, transferable, and craft-only. Reject anything
   that is really project knowledge and say where it should go instead.

4. **Separate the verification lessons.** For each proposed lesson, ask whether it names a
   mechanical condition: *did the thing run*, *did the change apply*, *is a pass actually a result*.
   Those are not finished as prose. Say what check would assert each one, in which project, and
   treat the lesson as still open until that check exists. A judgement lesson needs no check and
   writing it down is the whole of the fix.

5. **Consolidate if full.** `LEARNED.md` is capped at 25 lines. If adding would exceed it, you must
   merge or drop first — propose which. A lesson that has become automatic no longer needs writing
   down. Do not silently truncate; show them what you are removing.

6. **Write** the updated `LEARNED.md`, clear the consumed notes, and tell them to run
   `cto build && cto sync` for it to take effect. Learning is not live until then.

## Keep it short

Show the diff, not an essay about it. They can read.
